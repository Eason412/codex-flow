# 怎么拆：完整判据、依据与实例

SKILL.md「怎么拆」是本文的摘要。拿不准形状、或要向用户说明拆法依据时读本文。

主框架是 Anthropic《Building effective agents》。我们的结构就是文中的 orchestrator-workers：Claude 是编排者，看过具体工作后现定子任务，交给 Codex 执行，再汇总结果。文章的总原则是先找最简单的做法，只在确实能改善结果时才加复杂度。下面每条都对应文中的一种模式；按工种拆、按时长拆在文中和其他来源里都找不到依据，开工前也估不准时长，所以不用。补充依据：claude.com《Building multi-agent systems》（按上下文边界拆）、Claude Code subagents 文档、OpenAI Codex subagents 文档、ADaPT 论文（2026-10-03 调研）。

1. **先用最简单的做法**（文章总原则）：分界主要看能不能写成一份自包含的说明；但很小的改动（例如改一个函数、几行）派出去不划算，不单独派任务：我手上有就直接改，是某个 Codex 任务发现的问题就用 `-r` 接着它的对话让它顺手改。
   - 主 agent 自己做：要用到本次对话里的上下文、要边看效果边改、原因不明且还提不出能分开验证的假设，或者是确定性的机械替换（每处改法都一样、不用看上下文判断，用脚本一次改完）。
   - 派一个任务：能写成自包含说明、边界清楚的一件事，用 run.sh，不写 flow；按第 5 条要配验证任务时（diff 大到读不完，或规格得专门构造反例才验得出来）例外。
2. **子任务现定，一个任务管一件完整的事**（orchestrator-workers：子任务由编排者按具体输入决定，不预设）：
   - 先探路再拆：列出要改的文件、调用点、现有测试，再定任务，不套上一次的计划或示例。
   - 按上下文边界拆，不按工种拆：同一功能的实现、测试和文档归同一个任务；不把规划、实现、测试拆成先后几个任务，也不“一个写功能、一个写测试”。几个模块互相调用、要一起改，就是一个任务，不论多大。
   - 同一功能的两部分之间已经有写成文档的契约（例如接口的路径和字段），各自不看对方代码也能写完，就算两个上下文，可以拆。
3. **并行**（parallelization）：
   - sectioning：几件事各有不重叠的写入范围，而且每件都能在看不到别的任务代码的情况下写完，才放进同一阶段并行。只读任务互不依赖就能并行：调研按独立问题分，每个问题一个；诊断只在有几个能分开验证的假设时才并行。
   - voting：同一件事让几个任务各做一遍、取多个视角，用在需要多个视角或多次尝试来提高把握的时候（文中原话），例如几种架构方案的取舍，每个方案一个任务各自评估，由主 agent 比较定夺。
   - 共享文件指同一 flow 里不止一个任务要改的文件（常见的是根 README、CI、依赖清单和锁文件），不写进任何任务的 `writes`，由主 agent 最后统一改并自己核对。只有一个任务要改的（包括 CI、依赖清单，以及它所在模块的 README 和 SKILL 文档），归那个任务；只派一个任务时，它要改的都归它。
4. **先后只来自真实依赖**（prompt chaining：每一步处理上一步的产出，中间加检查关口）：
   - 后一个任务要用前一个的产出（调研结论、定下的接口契约、实现结果）才分先后；只有部分任务有依赖时用 `after` 做流水线，不让快的等慢的。
   - 关口能写成命令的放进 `checks`；要判断的（读调研、定规格、定修法）由主 agent 当关口：调研和诊断之后由主 agent 读结论、写规格或定修法，再派下一批，不在同一个 flow 里一路跑到底。
5. **验证**（evaluator-optimizer：有清楚的评判标准、反复修改能看到改进时才值得）：看验收是否独立于实现者。
   - 正确性由实现者以外的东西证明，例如改动前就有的测试、行为对照脚本、参考实现，就把它写进 `checks`，不加审查任务。旧测试覆盖不到这次改动的行为（例如只测了正常路径）时不算，按下一点处理。实证：2026-10-03 两个大文件拆模块，旧测试和 patch 对照脚本放进 checks 后，Astra 审查又核对了 30 组命令行输出和 72 次示例执行，没有发现任何行为回归，只提了 1 个轻微的结构建议。用旧测试证明拆分后行为不变时，委派说明允许改测试的导入，以及按文件名列出源码的夹具（例如把文件逐个复制到隔离目录的列表），断言和期望值不改；实证：同日 codex-flow 执行器拆模块，规格只准改 import，有 2 个按文件名复制源码的测试因此没过验收。
   - 新行为的测试由实现者自己写，只能证明它想到的情况。默认由主 agent 看 diff、对照规格核对、跑一次。只有两种情况才加一个黑盒验证任务：diff（增删合计）超过约 500 行或跨三个以上模块，主 agent 读不完（本仓库的工作口径，来源没有给数字）；或者规格要求得专门构造反例才验得出来（检查规则的误报和漏报、排版规范逐条核对、多种输入格式的边界）。实证：2026-10-03 project-docs 的实现自带 58 项测试全部通过，按规格黑盒验证仍复现了 3 个主要问题。
   - 改动量按每个任务分别算；开工前拿不准就先不加，任务做完由主 agent 看过 diff 再决定要不要补一个验证任务。验证任务按规格逐条验、跑完整测试、自己构造反例，用 `after` 接在被验的任务后面；发现的问题由主 agent 判断：小改动主 agent 直接改，或用 `-r` 让发现它的验证任务顺手改；改动较大才用 `-r` 交回原实现者修。修完由主 agent 复核，不再自动送审。并行的几个任务各自按这条判断，每个任务最多配一个验证任务；单个任务要配验证时写成两个任务的 flow，不用 run.sh。
   - 没有自动验收的产出（翻译、调研报告、文档），`checks` 写能跑的结构检查（例如双语结构对齐）；没有能跑的就不写 `checks` 字段，由主 agent 读结果核对。
   - 用户要求审查或交叉核对时，照用户说的做。
6. **模型按难度分配**（routing：常见的交给更省的模型，难的交给更强的模型）：实现和验证默认 `gpt-6.1-sol` / `high`。`gpt-6-astra` 在有必要时用，典型的是非常重要（出错代价很高）、非常难（正确性很难判断，例如并发、安全）或很难做决定的事；不把它当成每个 flow 的默认审查者。
7. **数量从少开始，跑偏再拆**：任务数等于第 3 条数出来的独立单元数，不为对称凑数；调研按问题定，简单查找 1 个，对比两三个方向 2–4 个。开工前不预先切得很细；15 分钟提醒时如果看到任务卡住、反复失败或越做越散，停下来把出问题的那一块拆成范围更窄的新任务（ADaPT：执行失败时才拆）。
8. **委派说明和透明**（文章三原则之一：把规划步骤明确展示出来）：每个任务写清目标、要读的输入、写入范围、不做什么、验收命令和回复格式。派任务前（run.sh 或 flow）告诉用户派几个、分几个阶段、用什么模型，以及各自依据上面哪一条。
